# Historical negative round playtime: evidence-based repair

Scope: RCON3 and RCON4 only. Requested 25 October 2026. This is a historical
data repair, not another application rollout and not a change to moderation.

## Meaning of the replacement

The replacement is **connected seconds within the round**, supported by recorded
connection/disconnection events. It does not claim to measure time spawned,
alive, moving or fighting. No arbitrary warmup/cooldown subtraction is used.
The runtime guard introduced by `373ab10f` remains a separate change.

Examples found in the authoritative database:

- A connection at 18:29:14 UTC, a round ending at 18:30:05 UTC, and a matching
  disconnect at 19:08:30 UTC on 24 October establish 51 seconds in the round.
  The old stored value was -49 seconds. This candidate was **not applied**:
  final validation also found an older unclosed session from 21 October.
  The strict session-consistency gate leaves it for separate review.
- A player connected before the next round, which began at 18:32:23 UTC,
  and disconnected at 18:32:33 UTC: 10 seconds, not the old -170 seconds.

## Selection and conservative exclusions

The read-only snapshot selects only `player_stats.time_seconds < 0`, joined to
`map_history.server_number IN (3,4)`. Full original rows are retained privately.
For each candidate, inspect the same internal player ID and server, not a name:

1. Actual `MATCH START` and `MATCH ENDED` logs must exactly confirm the saved
   boundaries, without an additional intervening round boundary.
2. Require complete, ordered CONNECTED/DISCONNECTED pairs. Look one day before
   and after the round to establish sessions crossing round boundaries.
3. Require exact agreement with the same-server `player_sessions` timestamps.
   Session rows alone are insufficient: historical close-session code can pick
   the player's latest session without filtering the server.
4. Deduplicate identical transitions; reject ambiguous repeated connects,
   unmatched disconnects, missing ends and conflicting/overlapping sessions.
5. All recorded player activity in the round must lie inside those sessions.
   Saved kills/deaths/teamkills must reconcile with the available raw events.
6. Sum each session's intersection with the round. Only strictly positive,
   bounded results qualify for this repair. Even zero-length boundary cases
   remain unchanged rather than using zero as a generic fallback.

Rounds longer than four hours are conservatively excluded, not declared
impossible. Missing logs do not establish absence. Agreement between retained
logs and sessions cannot prove that no upstream event was ever dropped.

## Execution safeguards

- Fresh complete database dump, table-of-contents check and full archive decode
  before even the rollback rehearsal. Retain the original row/evidence files.
- Deterministic plan, evidence and code hashes. Recalculate every replacement
  from evidence rather than trusting supplied replacement values.
- A repeatable-read transaction and advisory lock prevent overlapping repairs.
  Lock selected old rows, recheck complete rows and maps, and re-read the raw
  connection/activity/session evidence before any update. Drift aborts.
- Only `time_seconds`, `kills_per_minute` and `deaths_per_minute` may change.
  Rate fields use the existing application's rate formula with the repaired
  duration. All combat counts, scores, identities and other fields stay intact.
- First exercise the real SQL updates and verification with ROLLBACK. Apply
  only the identical plan after a successful rehearsal. Verify again in a new
  read-only transaction after COMMIT. A fully applied plan is idempotent; a
  partly changed or otherwise altered row aborts instead of overwriting it.
- No RCON/game commands, global cache flush, service restart or config change.
  Evict only the exact repaired historical-scoreboard cache keys on RCON3/4,
  including their stale copies, so the UI can fetch the corrected database data.

## Atomaresecho HLLV correction

The game server returned `wdeva_domination_day`, `Domination` and faction ID 6,
while the instance used `HLL_GAME=hll`. This caused repeated
`Game mode 'domination' is not supported by the 'hll' game profile` failures both
before and after the application upgrade. A read-only HLLV probe parsed the same
live response successfully.

After explicit approval, `HLL_GAME=hllv` was persisted in the instance `.env` and
the active compose model for the backend, supervisor and background worker. The
previous `.env` and compose model remain in `env.before-hllv` and
`compose.before-hllv.json`. The live game state now parses correctly, and the
post-correction event-loop, automod, routines and API log scans found no errors.
Authenticated read-only requests to `/api/get_gamestate` and
`/api/get_live_game_stats` both returned HTTP 200 with `failed=false`. A subsequent
normal map change to `wdeve_warfare_day` was correctly recognized as `warfare`.
No Redis flush or historical database rewrite was performed.

The initial deployment gate found an inactive legacy autobalancer with no state,
status, armed player or worker heartbeat. It allowed the scoped restart only
after proving the empty state while holding the existing execution lease and
the leadership advisory lock. No configured automation mode was changed. The
autobalancer and live-map workers were absent from the original supervisor
configuration and were not enabled by the application update. No deployment
execution lease remains. The autobalancer was activated separately after
explicit approval, as recorded below; the live-map worker remains unchanged.

## Outstanding external issues

### Existing game-server connection errors

Ente1's event loop had 18 `UnicodeDecodeError` occurrences in the hour before its
restart, with two afterwards in the checked window. HLL1 had a connection
reset/broken-pipe error before and after its restart and subsequently supplied
fresh live data. Ente2 had no event-loop errors in the checked post-rollout window.
These are not evidence of a new migration or database integrity failure.

During verification, SQL diagnostic lines beginning with `[` were initially
misclassified as timestamped log entries; the scanner was corrected to require
an actual timestamp. The corrected scan found no new integrity errors.

The hosted deployment check also required a timestamp-parser compatibility fix
for the host's Python version. It was rerun successfully without database
downgrade or application rollback. No release image was modified.

# RCON3 scheduled database and session journal backups

The RCON3 host runs `rcon3-scheduled-backup.timer` at 05:00 Europe/Berlin. The timer invokes `rcon3-scheduled-backup.service`, which runs `scripts/rcon_paired_backup.py` against the PostgreSQL container shared by the RCON installations. Backups are stored in private timestamped directories under `/root/hll_rcon_tool/.deploy-state/scheduled-backups`. This is an on-host copy, so it does not protect against loss of the host or its disk.

The job takes short-lived PostgreSQL SHARE locks on the session-event tables, exports a repeatable-read database snapshot, and snapshots each existing per-server SQLite journal before releasing the locks. It keeps the exported snapshot alive while `pg_dump` runs without those write locks. Each dump is fully decoded with `pg_restore` and each journal is checked with SQLite `integrity_check`. A successful run writes `manifest.json` with timestamps and SHA-256 hashes; a failed or interrupted run keeps an `INCOMPLETE` marker and must not be treated as a successful backup. An overlapping invocation fails rather than running concurrently. The job refuses to begin when less than 10 GiB is free, and it does not delete older backups automatically. Monitor available space and failed systemd jobs; there is no notification integration in this setup.

The session journal is not installed on RCON3 yet. Before its session migration is installed, a backup may contain no journal. Once the `unidentified_session_event` table exists, the job requires `server-3.sqlite3` in `/root/hll_rcon_tool/supervisor_data/session-events`; a missing journal makes the run fail. Do not advance that schema without ensuring the corresponding journal is present and the service is running with the verified journal implementation.

Check the schedule with `systemctl list-timers rcon3-scheduled-backup.timer` and the latest run with `journalctl -u rcon3-scheduled-backup.service`. To perform a recovery rehearsal, use the database dump and all journal files from the same completed directory, verify their hashes, and restore them into isolated PostgreSQL and new journal paths. For production recovery, stop all relevant writers and restore the matching database and journal set together. Do not mix backups from different runs.

The isolated rehearsal used a disposable PostgreSQL container and synthetic journal, restored both, checked failure on a missing required journal, and confirmed that a deliberately slow export no longer blocks later session writes or incorporates writes made after the exported snapshot. It did not perform a production restore.

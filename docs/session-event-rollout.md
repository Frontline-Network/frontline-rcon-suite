# Session event rollout and historical timestamps

New session events retain an absolute UTC instant alongside the existing wall-clock columns. The existing columns are not bulk-converted. New session durations and serialized start/end values use the absolute instants when available. Older values without that metadata retain their previous interpretation; their historical timezone cannot be inferred reliably from the value alone.

If a connect or disconnect cannot safely be matched, it is retained for review. Operators with player-profile viewing and raw-command permissions can inspect the event in the player records view. A connect can be linked to a selected legacy session, recorded as a distinct session, or discarded; an unmatched disconnect can only be discarded after verification. Each decision requires a reason and is recorded in `session_event_resolution`. Linking a legacy start does not reinterpret an unknown legacy end time. Review may be needed before all affected events can be associated; no game-server action is performed by these decisions.

For an open legacy session, a unique matching connect log with the same player, server, wall time and embedded absolute timestamp can establish its UTC instant. Duplicate rows, missing logs and ambiguous matches are not inferred. `HLL_SESSION_LEGACY_UTC=true` is a separate opt-in to interpreting legacy session timestamps as UTC without such a log, and is honored only when the process itself uses a fixed UTC timezone. Set it only after verifying that the affected historical values were recorded as UTC; the current container timezone alone is not evidence of that. Without evidence or this explicit setting, legacy wall-clock matches remain for review rather than being silently assigned an instant.

All session writers sharing a database must run the updated version before server isolation and out-of-order handling are guaranteed. Older writers do not populate absolute event fields and may still change the wrong session. Stage the additive schema before starting an updated writer. During rollback, retain the new columns and pending/audit tables: dropping them discards absolute instants and unresolved events. The Alembic downgrade is for isolated tests or after those records have been separately resolved and archived.

The supervisor records session events in a per-server SQLite journal under `HLL_SESSION_JOURNAL_DIR` (default `/data/session-events`), which must be a private, persistent local filesystem with sufficient space. Back it up alongside the shared database; restoring only one of the two can replay or lose unresolved work. The first activation time is stored in the journal and older log entries are not imported retroactively. Losing the journal resets that cutover and can lose pending events. If the journal cannot be written, the log batch is not dispatched; investigate disk space and permissions promptly because the game server retains logs for a finite time.

For a coordinated backup, first stop every writer of the shared session tables and every corresponding journal; verify that they are stopped before taking either snapshot. Save and verify the PostgreSQL dump and use `python -m rcon.session_event_backup SOURCE DESTINATION` for each journal. This tool uses SQLite's online backup API, checks the snapshot and refuses to overwrite an existing destination. Record which PostgreSQL dump and journals belong together and securely retain the pair. A journal snapshot taken while writers run is internally consistent, but is not guaranteed to match a PostgreSQL dump taken at another instant.

To rehearse restoration, restore the paired PostgreSQL dump into an isolated database and run the same command with the journal backup as `SOURCE` and a new path as `DESTINATION`. Validate pending events and audit records before starting an isolated writer. Production recovery requires all relevant writers to remain stopped while the matched database and journal set is restored. The tool deliberately refuses to replace an existing file; preserve the current journal and do not restore an older journal against a newer database, or vice versa, without an explicit reconciliation procedure.

Connect or disconnect records without a player ID are preserved separately and never automatically assigned by name. The supervisor transfers them to the shared database; operators with player-profile permission can review them in the web interface. Discarding requires the additional raw-command permission and a reason; the database retains the operator and reason. This does not associate an event with a player. Completely anonymous records cannot be assigned without independent evidence, and an audited association workflow is still required. During a database outage, an administrator with host access can inspect the local journal inside the relevant supervisor with `python -m rcon.session_event_journal_cli /data/session-events/server-3.sqlite3 --server 3`. The output includes raw events and may contain player names; treat it as operational data. Local discard is only available before transfer and is serialized with it. Do not remove the journal as part of a routine container replacement.
